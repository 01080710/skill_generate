# 機敏資訊規則（/day-start、/day-end 共用，最高優先）

日誌、判斷點檔案、commit 訊息、PR 內文都會進 git 歷史；**push 之後刪檔也刪不掉**。所以只寫「程式改了什麼、為什麼、驗證了什麼」，**不寫任何資料本身**。拿不準的一律當成機敏，改寫後再寫。

## 分級

**🔴 絕對不能寫（沒有例外，使用者要求也改用描述）**
- 帳密與金鑰：密碼、token、API key、App ID / Secret、`.env` 的值、私鑰、憑證、JWT / cookie / session、含帳密的連線字串

**🟡 預設不寫（只有使用者逐條確認才保留）**
- 個人資料：真實姓名、email、電話、員工編號或其他對得到個人的代號、帳號、地址、生日
- 業務資料：資料庫 / 試算表的實際內容與範例列；特定人、團隊或日期的排班、請假 / 加班與原因；**看得出營運空窗或人力配置的具體時段與人數**；客戶與交易資料
- 內部環境：內部主機名稱、IP、內部網址（含協作工具的文件 / 試算表連結與 token）、公司網域、帶使用者名稱的本機路徑
- 原始輸出：log、錯誤訊息、SQL、查詢結果、截圖上的文字——含上述任何一項就不能原樣貼

## 改寫方式

- 人 → 角色或泛稱（「一位 Agent」「某主管」），不寫姓名或編號；日誌的「交接」對象用 username
- 資料 → 寫驗證了什麼、結果符不符合，不寫值（✅「用正式資料驗證缺口偵測正確」；❌「某團隊 10/18 07:00–15:00 無人」）
- 數量 → 只到看不出內容的量級（✅「約 4 萬列」；❌「某團隊某天剩 1 人」）
- 路徑 → 專案內的相對路徑；金鑰 → 只寫「放在 `.env` 的 `XXX` 變數」，不寫值

## 誰負責什麼

| 程式（`daily.py scan`、git hook） | Claude（人工讀一遍） |
|---|---|
| 🔴 格式明確的金鑰（私鑰、AKIA、ghp_、sk-、xox、JWT、連線字串帳密、`password="…"`）——任何檔案都擋 | 姓名、業務資料（值、時段、人數、範例列）——正規表示式抓不到 |
| 🔴 `token: …` 這類寫法、🟡 email / 電話 / IP / 網址 / 本機路徑 / 長亂碼——只掃日誌、判斷點、commit 訊息 | 決定 🟡 要怎麼改寫，列原句與改寫給使用者確認 |
| 專案自訂格式：根目錄 `.journal-sensitive-patterns`（一行一個正規表示式，例如 `EMP[0-9]{4}`） | |

`scan` 只回報「位置＋規則名稱」，不輸出內容。

**什麼時候可以出現原文**：
- ✅ 收工時在對話中把 🟡 的原句與改寫句列給使用者本人確認——這是使用者自己寫的內容，不出這台電腦。
- ❌ 寫進 git 的任何東西（日誌、判斷點、commit 訊息、PR 內文）、開工 / 收工摘要、給隊友看的交接：一律只寫改寫後的說法，或「檔案:行號 有疑似機敏內容」。
- 🔴 帳密與金鑰連對話中確認也不要重複貼出完整值，只說位置與規則名稱。

## 處理結果

- 🔴 命中 → 改寫或刪除，**不得 commit / push**（hook 也會擋，不要用 `--no-verify` 繞過）。若這個值**已經在之前的 commit 或已 push 的歷史裡** → 停下來，請使用者**立刻更換（rotate）這組帳密**（從歷史刪除並不能讓它失效）；清理歷史要改寫 git 歷史，由使用者決定，不要自己做。
- 🟡 命中或人工讀到 → 預設改寫；在對話中列出原句與改寫後的句子給使用者確認，只有使用者明確說「這句保留」才保留。
